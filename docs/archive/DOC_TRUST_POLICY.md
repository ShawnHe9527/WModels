# ⚠️ 文档可信度政策（用户 2026-10-10 明确指令）

> 用户原话：
> 「你不要全信文档，文档中有一些是前面有缺陷的实验，**不要被前文的缺陷设计错误引导**。
>   我的设计是按照 **A 每段独立**设计的，所以**选取 A 方案，并行实验**。
>   ANN_V2 版本之前的文档中你需要重点关注的有：
>   **编程错误经验、先前踩的坑、以及部分实验结果**，
>   不要被 V2 之前的错误实验设计而错误引导。」

---

## 1. 文档分三类，只信其中两类

| 类别 | 可信度 | 处理方式 | 判别特征 |
|---|---|---|---|
| **① 编程错误经验 / 踩过的坑** | ✅ **高可信，必须遵守** | 一律当**硬约束** | 陷阱清单、bug 记录、判据缺陷、事故报告 |
| **② 实验结果（数值）** | ✅ **可信**（是实测） | 可引用，但**必须核对协议与口径**是否仍适用 | 「实测 / 我们测了 / 数值是 X」 |
| **③ 实验设计 / 架构方案 / 论证** | 🔴 **低可信，需独立复核** | ⚠️ **不得当作前提**；要依据它决策前先自己验证 | 「应该 / 建议 / 最优解 / 因此我们采用」 |

**判别技巧**：看到「**实测 / 测了 / 数值是**」⇒ 类别 ②；
看到「**应该 / 建议 / 最优 / 因此采用**」⇒ 类别 ③，**要打问号**。

## 4. 由此确定的工作规则

1. **A 方案（每段独立网络）是用户定的** ⇒ 不再讨论共享网络（`ARCH_SHARING.md` 里的 B/C/D 作废）。
2. **文档的「论证」与用户设计冲突时，以用户设计为准。**
3. **我自己引入的新设计**（如 V2 的输入布局）也属于类别 ③ ⇒ 必须**自检 + 预先注册判据**，
   不能靠"设计文档这么写"来辩护。
4. **每写一个数字（维度/通道数/段数），先在代码里 grep 出来再写**（我已犯过两次：
   「2×193」、以及 V2 里的「4+2·nseg」）。
